# Architecture

Next.js 16 storefront (App Router, Cache Components, Tailwind v4) that consumes the Vendyx storefront API (GraphQL). Checkout is hosted by Vendyx: the storefront builds the cart and hands it off.

The rules here follow the Next.js docs bundled in `node_modules/next/dist/docs/`. When in doubt about an API, read its guide there, not from memory.

## Structure

```
src/
├── app/            routes only: layout, page, loading, error, not-found and route handlers
├── lib/
│   ├── vendyx/     Vendyx storefront API layer, server only (shared by every module)
│   └── <module>/   one folder per domain: product, collection, cart, customer, checkout...
├── shared/         components, hooks and utils shared by several modules
└── proxy.ts        optional; only for redirects or rewrites that need the request
```

- `@/` points to `src/`.
- `src/app/` has no business logic: each `page.tsx` and `layout.tsx` imports and renders what lives in `src/lib/<module>/`.
- Route groups `(group)` organize routes that share a layout without changing the URL, for example `(shop)` and `(account)`.

## Module

```
src/lib/<module>/
├── data/          get-<thing>.ts, server-only reads (Data Access Layer)
├── actions/       <action>.ts, Server Actions
├── pages/         <name>-page.tsx, one per route
├── components/    <component>/<file>.tsx, grouped by screen or piece
├── hooks/         use-<thing>.ts, client hooks
├── constants/     cache-tags.ts and module constants
└── utils/         <topic>-utils.ts, pure functions
```

A module only creates the folders it uses.

## Routes

```tsx
// src/app/products/[slug]/page.tsx
import { ProductPage } from '@/lib/product/pages/product-page';

export default function Page({ params }: PageProps<'/products/[slug]'>) {
  return <ProductPage params={params} />;
}

export { generateMetadata } from '@/lib/product/pages/product-page';
```

- Use the global `PageProps<'/route'>` and `LayoutProps<'/route'>` types; they're generated by Next.
- `params` and `searchParams` are promises. Pass them down and `await` them in the component that needs them, inside `<Suspense>`.
- Routes with a known set of params (collections, featured products) export `generateStaticParams` to be prerendered.
- Every route with its own data has `loading.tsx` or a `<Suspense>` with a skeleton that matches the final layout.
- Missing resources call `notFound()` from `next/navigation`; each segment that needs it has its own `not-found.tsx`.
- `error.tsx` (Client Component) handles unexpected errors per segment; `global-error.tsx` covers the root layout.

## Server and Client Components

- Everything is a Server Component by default. `'use client'` only goes on the interactive leaf that needs state, effects, event handlers or browser APIs (variant picker, quantity input, gallery), never on a page or layout.
- A Server Component can be passed as `children` to a Client Component to keep it on the server.
- Props that cross to a Client Component are serializable and minimal: only the fields it renders.
- Context providers are Client Components rendered as deep as possible, wrapping only what needs them.

## Vendyx API (`src/lib/vendyx`)

The Data Access Layer recommended by Next for new projects. It's the only place that talks to Vendyx.

- Every file starts with `import 'server-only'`.
- It's the only place that reads `process.env` for Vendyx (`VENDYX_API_URL`, `VENDYX_STOREFRONT_API_KEY`). The API key never reaches the client and never uses the `NEXT_PUBLIC_` prefix.
- A single `vendyxFetch` sends the GraphQL request with the storefront API key and, when there is one, the customer's access token read from cookies.
- Operations (`*_QUERY`, `*_MUTATION`, `*_FRAGMENT`) live in `src/lib/vendyx/operations/<domain>-operations.ts`.
- Responses are mapped to minimal DTOs with only what the storefront uses. Raw API responses don't leave `src/lib/vendyx`.
- Business errors from the API are translated to a code and a message for the customer in `src/lib/vendyx/errors/<domain>-errors.ts`.

## Reading data

Reads live in `src/lib/<module>/data/` and call `src/lib/vendyx`. Components never call `vendyxFetch` directly.

### Public data (catalog)

Products, collections and shop data don't depend on the request: they're cached and become part of the static shell.

```ts
import { cacheLife, cacheTag } from 'next/cache';

import { getVendyxProduct } from '@/lib/vendyx/product';

import { ProductCacheTags } from '../constants/cache-tags';

export const getProduct = async (slug: string) => {
  'use cache';
  cacheLife('hours');
  cacheTag(ProductCacheTags.Product(slug), ProductCacheTags.Products);

  return getVendyxProduct(slug);
};
```

- Every `'use cache'` has a `cacheLife` and at least one `cacheTag`.
- Tags come from `constants/cache-tags.ts` (`<Module>CacheTags`). Never loose strings as tags.
- A cached function never reads `cookies()`, `headers()` or `searchParams`. If it needs a runtime value, it receives it as an argument.

### Per-customer data (cart, account, orders)

Depends on cookies, so it's not cached with `'use cache'`.

- The component that reads it goes inside `<Suspense>` with a fallback, so the rest of the page stays in the static shell.
- If the same value is read several times in one request (the current customer, the cart), wrap the function with `cache` from `react`.
- If it needs a lifetime to be included in prefetches, use `'use cache: private'`.

### Parallel reads

Independent reads start together with `Promise.all`, or in sibling components each with its own `<Suspense>`. Don't chain `await`s that don't depend on each other.

## Mutations

Mutations are Server Actions in `src/lib/<module>/actions/<action>.ts`, with `'use server'` at the top of the file.

```ts
'use server';

import { updateTag } from 'next/cache';
import { z } from 'zod';

import { addVendyxCartLine } from '@/lib/vendyx/cart';

import { CartCacheTags } from '../constants/cache-tags';

export const addToCart = async (
  _prevState: ActionResult,
  formData: FormData
): Promise<ActionResult> => {
  const parsed = Schema.safeParse(Object.fromEntries(formData));
  if (!parsed.success) return { isSuccess: false, error: 'Invalid quantity' };

  const result = await addVendyxCartLine(parsed.data);
  if (!result.isSuccess) return result;

  updateTag(CartCacheTags.Cart);
  return { isSuccess: true };
};

const Schema = z.object({
  variantId: z.string().min(1),
  quantity: z.coerce.number().int().positive()
});
```

- A Server Action is a public endpoint: validate every input with zod and check the customer's session inside the action, never only in the UI.
- Return `ActionResult` (`{ isSuccess: true }` or `{ isSuccess: false, error, errorCode? }`). Expected errors are return values, not exceptions.
- Unexpected errors are logged and returned as a generic error.
- After a successful mutation, update the cache:
  - `updateTag` when the customer must see their change in the same response (cart, address, profile).
  - `revalidateTag` for stale-while-revalidate refreshes (catalog changed from outside).
  - `refresh` when the view depends on state outside the cache.
- `redirect` goes outside `try/catch`, because it throws.
- Return only what the UI needs, never the raw API response.

### Forms

- A form uses `<form action={action}>`. Without client feedback it can stay a Server Component.
- With pending state or errors, the form is a Client Component with `useActionState(action, initialState)`; it reads `pending` and `state.error`.
- A button that submits its own form reads its pending state with `useFormStatus`.
- Server Actions aren't used to read data.

## Checkout

The storefront doesn't build the payment page: once the cart is ready, it redirects to the Vendyx hosted checkout with the cart's identifier.

## Route Handlers

Only for what a Server Action can't do: webhooks (for example, revalidating catalog tags when something changes in Vendyx) and endpoints called by third parties. They live in `src/app/api/<name>/route.ts` and verify the request's signature or secret before doing anything.

## UI

- Links with `next/link` and fonts with `next/font`.
- Images with the plain `<img>` tag, never `next/image`: Vendyx already serves them optimized from its CDN. Every `<img>` has `alt`, `width` and `height`; images below the fold use `loading="lazy"`, and the main image of the page (the product's first image, the hero) uses `fetchPriority="high"`.
- Each route exports `metadata` or `generateMetadata`; product and collection pages use the product's or collection's data.
- Tailwind v4: the theme lives in `src/app/globals.css` with `@theme`. There's no `tailwind.config.js` and none is created.
